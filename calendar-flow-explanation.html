React State: UI as a Function of State

At its core, React views are declarative. The interface is simply a snapshot output of your current state variables at any millisecond in time.

  • Declaration: Inside `DashFinal.tsx`, state is declared with `useState(localIsoDate())`. This initial value matches today's local date string.
  • UI Event: When you click a date on the calendar, the browser fires an `onClick` handler. This calls `setDate(selectedIsoDate)`.
  • Reconciliation: Changing state notifies React that the UI snapshot is outdated. React schedules a re-render of the components that depend on `date`.
  • Effect Trigger: The hook `useDashData` wraps the API call in a `useEffect`. Because `date` is declared in the effect dependency array `[dateOverride]`, React automatically fires the hook's execution function whenever `date` changes.

First Principle Concept

State changes do not "draw" updates onto the screen directly. Instead, they change the input values of our rendering functions. React then compares the output virtual DOM with the actual DOM and changes only the nodes that differ.

React Hook Trigger 
// 1. Declaring state in component
const [date, setDate] = useState(() => localIsoDate());

// 2. Triggering update on interaction
<button onClick={() => setDate("2026-05-21")}>21</button>

// 3. Hook executing side effect on date change
useEffect(() => {
  async function load() {
    const data = await fetch(`/api/daily?date=${date}`);
    const json = await data.json();
    setDashboardData(json);
  }
  load();
}, [date]); // <-- Dependency triggers run

HTTP API Router: The Secure Broker

Browsers cannot query database instances directly. Doing so would require storing administrative credentials inside the client code, exposing them to any user who inspects the network panel or source files.

  • The Route Handlers: Next.js API Routes (located in `app/api/...`) act as server-side boundaries. The frontend sends HTTP requests to these endpoints.
  • Request Parameters: The date parameter is passed in the query string: `/api/daily?date=2026-05-21`. The Next.js API handler reads this via `req.nextUrl.searchParams.get("date")`.
  • Secure Execution: Inside the API route, the server initializes a database client using the private `SUPABASE_SERVICE_ROLE_KEY`. This key never reaches the client's browser.
  • Aggregation: The API router fetches data from multiple tables (spending, food, activities, calendar) concurrently using `Promise.all` and aggregates it into a single clean JSON payload.

First Principle Concept

API endpoints are boundaries of trust. The client asks "What happened on May 21?". The server validates the request format, executes database queries, aggregates results, and replies with structured JSON. The server completely hides SQL details from the user.

app/api/daily/route.ts 
export async function GET(req: NextRequest) {
  // Extract date query param
  const url = new URL(req.url);
  const date = url.searchParams.get("date");

  // Query Postgres securely on server side
  const { data, error } = await supabase
    .from("spending")
    .select("id, item, amount, category, time_local")
    .eq("occurred_date", date);

  // Return JSON response
  return NextResponse.json({ date, spending: data });
}

PostgREST: Declarative HTTP to SQL

Supabase does not run a custom server runtime for database client libraries. Instead, it relies on PostgREST, a standalone web server that sits directly in front of PostgreSQL and compiles REST requests into SQL queries automatically.

  • Supabase SDK Translation: When you execute `.from("spending").select("...").eq("occurred_date", date)`, the JS client compiles this chain into a REST request path.
  • REST Syntax: The JS request target becomes `https://.supabase.co/rest/v1/spending?occurred_date=eq.2026-05-21`.
  • SQL Compilation: PostgREST parses the HTTP headers and query params. It writes a single SQL string, injecting the arguments into placeholders (`$1`, `$2`) to prevent SQL injection.
  • One Database Roundtrip: Unlike ORMs that do multiple client-server operations, PostgREST compiles everything into a single SQL statement, requesting rows as a JSON payload formatted inside PostgreSQL itself.

First Principle Concept

PostgREST treats database tables as endpoints and column filters as query parameters. A URL predicate like `amount=gt.100` compiles directly to `WHERE amount > 100`. It acts as an automated compiler translating URLs into SQL.

HTTP Url Request -> PostgREST 
# Client library sends HTTP GET under the hood:
GET /rest/v1/spending?select=id,item,amount&occurred_date=eq.2026-05-21
Host: your-project.supabase.co
Authorization: Bearer <SERVICE_ROLE_KEY>

# PostgREST compiles this into database SQL:
SELECT 
  id, item, amount 
FROM 
  public.spending 
WHERE 
  occurred_date = $1;  -- $1 is bound to "2026-05-21"

PostgreSQL: Scanning B-Tree Indexes

Once the SQL query reaches PostgreSQL, the database engine executes it. If our table has millions of rows, looking at every single row (Sequential Scan) would make the dashboard lag. This is where database indexes are essential.

  • The Table Layout: The database table stores data values on pages in memory/disk. Without indexes, Postgres must inspect every page sequentially.
  • The B-Tree Index: We created an index: `create index spending_date_idx on public.spending (occurred_date, time_local)`. This builds a sorted tree structure.
  • Index Scan: Instead of searching the whole table, PostgreSQL searches the B-Tree index by matching key values. This locates the exact page addresses of rows where `occurred_date = '2026-05-21'` in logarithmic time O(log N).
  • Sorted Results: Because the index includes `time_local`, the index scan reads rows in pre-sorted chronological order, bypassing the need for a separate Sort execution step.

First Principle Concept

Indexes are pre-sorted lookup tables. By indexing the columns used in filters (`WHERE`) and sorts (`ORDER BY`), PostgreSQL can find matching rows instantly and read them in order, reducing query latency from seconds to microseconds.

PostgreSQL Execution Plan 
-- Executed Database Schema Index
CREATE INDEX spending_date_idx 
  ON public.spending (occurred_date, time_local);

-- EXPLAIN ANALYZE shows how database scans:
Index Scan using spending_date_idx on spending
  Index Cond: (occurred_date = '2026-05-21'::date)
  Filter: (amount > 0)
  Rows Returned: 3
  Execution Time: 0.124 ms  -- O(log N) Lookup!
